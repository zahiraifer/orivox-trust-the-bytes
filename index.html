Trust the Bytes, Not the Label: How Orivox Proves What Is Running

By Zahi Raifer

Zahi Raifer has 23 years of experience in AI, Python, .NET and databases. He is the founder of Orivox, where he focuses on product development, not sales.

Disclosure: this article was drafted with the help of an AI assistant and reviewed by the author. All facts come from Orivox's own description of its system.

Most writing about AI website builders is about the model. This piece is about something duller and, for a customer, more important: how a line of code travels from a developer's screen to the server that edits your site, and how we know, afterwards, that it really arrived.

The rule: nobody edits production by hand

At Orivox, code never changes on a production server by hand. There is one path, and every change takes it:

  1. The code is pushed to the repository.
  2. It is pulled into the development environment.
  3. It is verified there.
  4. It is promoted to production from an admin dashboard.

The dashboard is not a convenience button. It records every release and keeps a backup of what it replaced. So every production state has a history entry, and every previous state has a copy.

Development is a real environment, not a laptop

The development environment has its own copy of the web app and the editing service, with its own site files. That separation matters: new code meets real usage before production sees it, but it does so against files that are not a customer's live site. A mistake in development damages development.

Order matters: the callee ships first

The system is two codebases: a web app, and an editing service that the web app calls over HTTP. Releases follow that dependency. The editing service goes first, then the web app that calls it.

The contract between them changes in three steps: make the change additive, release it, and only then start using it. Seen from the release path, this is what lets the two services ship independently. At no moment is a new web app calling an editing service that does not yet understand it, and at no moment does an older caller break because a field it relied on disappeared. The contracts are pinned by tests on both sides, so "additive" is checked, not assumed.

The standby is the last rehearsal

Production runs on two identical servers; only one takes traffic at a time. A release goes to the standby first and is checked there before it takes a single customer request. The web app and the editing service have separate switches, so each can move between servers on its own, which fits naturally with the callee-first order above. Because site files live on shared storage mounted by both servers, a switch moves no files. Rolling back is moving traffic back.

Verifying by content

Here is the step this article is really about. When a release is done, how do you know what is running?

The common answer is a version label: a tag, a build number, a string in a config file. Labels are claims. They can be stale, copied, or set by a step that succeeded while the step after it failed.

Orivox confirms a release by hashing the files that are actually running, not by trusting a version label. The question being asked changes from "what does the server say it is?" to "what is it, byte for byte?" If the hash matches what was verified in development and on the standby, the release is what we tested. If not, we know before a customer does.

This is the same philosophy the editing engine uses on customer pages, where a claim of success needs a real change. In both places, the system does not accept a report; it checks the thing reported on.

Nothing restarts behind our back

A verified state is only useful if it stays put. Services restart only when we release; operating-system updates never bounce the application on their own schedule. The running code changes at the moments we choose, through the path above, and at no other time.

Watching from the outside

Inside checks can agree with each other and still miss what a customer sees. So every five minutes a probe walks the AI connector end to end, from discovery and sign-in to a real tool call, and emails an incident report on any failure and on recovery. When something does fail live, the fix comes with a replay test, so the same failure becomes a permanent check.

The shape of it

Put together, a release at Orivox is a chain of evidence rather than a sequence of hopes:

  • one path into production, with a recorded release and a backup of what it replaced;
  • a separate development environment with its own files;
  • callee first, additive contracts, tests on both sides;
  • a rehearsal on the standby before any traffic moves;
  • confirmation by hashing what is actually running;
  • no unplanned restarts;
  • an outside probe every five minutes.

None of it is clever. Each step is enforced by code or by process rather than by care, so it holds on a busy day as well as a quiet one.
